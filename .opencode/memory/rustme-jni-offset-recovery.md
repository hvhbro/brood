Проект rustme (C:\Users\Admin\Desktop\rustme): JNI-инструменты для защищённой Minecraft-сборки (fork JVM с протектором Astraea). Офсеты в `jni/dll/src/offsets.h` (4 RVA внутри jvm.dll) надо обновлять после каждого обновления игры.

**Методика (отработана 2026-09-02, скрипты в `tools/`):** mdump.py — свой парсер минидампа (ModuleList + Memory64List). Поиск:
- invoke-таблица: паттерн 3 NULL + 5 указателей в .text (в .rdata); main_vm — qword в .data, указывающий на неё (проверка: in_jvm≈4/outside≈6 ссылок).
- kNativeTableRva («expected», .rdata): layout [0]=.text(конец .text), [1]==[2], [3]=NULL, [4]=0xB914, [5]=0xB4B0 — искать у начала .rdata; калибруется по совпадению RVA функций между билдами.
- kObservedLiveEnvTableRva («live», .data): сигнатура JavaThread JNIEnv — qword[site]=таблица, qword[site-0x40..-0x28]=4 восходящих указателя (p,p+8,p+0x10,p+0x18); даёт ~30 сайтов на поток.
- Валидация: старый дамп D:\1proekts\rustme\rustme_19600_1782646686.dmp содержит ground truth (0xDEBF68/0xBEBB10/0xB628F8/0xDEC0F0) — методика воспроизводит все 4.

Офсеты нового билда (дамп rustme_26116): kJavaVmRva=0xE6D248, kInvokeTableRva=0xC5DCD0, kNativeTableRva=0xBD2898, kObservedLiveEnvTableRva=0xE6CAF0.

**2026-09-03, runtime-проверка:** все 4 RVA попадают (invoke match=YES, live env vtable match=YES), но **слот 209 больше не FindClass** — протектор Astraea перемешивает порядок функций в env-таблице, и в новом билде перестановка другая. Обновления требуют не только адреса таблиц, но и карту «слот→функция».

**План восстановления карты слотов (согласован с пользователем, пока не выполнен):**
1. Офлайн-дифф двух дампов: эталонная (.rdata) таблица указывает на thunks в конце .text ([0]=.text-конец, [1]==[2]); разрешив каждый thunk (jmp), сопоставить слоты эталонной ↔ живой таблицы = перестановка протектора. Карта функций старого билда известна (discovered-offsets.md: FindClass=209, ExceptionClear=202, GetObjectClass=221, GetArrayLength=162 — это слоты живой таблицы). Если перестановка одинакова в билдах — переносится на новый.
2. Runtime-пробы из DLL: GetVersion (возвращает 0x00010006), GetJavaVM (ложит main_vm), ExceptionOccurred/Clear, кандидаты FindClass под SEH. Вариант: автодетект карты при старте DLL вместо хардкода — переживает будущие сдвиги.
3. Дизасм .text по константам (GetVersion содержит 0x10006) — минус: часть кода в упакованных секциях (.orn, ._|n), может быть виртуализирована.

Нюансы: ~8-9 записей живой таблицы указывают мимо jvm.dll (хуки Astraea) — офлайн-дифф их не разрешает; FindClass, судя по старому билду, не захучен. В live-таблице нового билда первые 3 слота NULL, слот reserved1 занят (не «4 NULL» как в стандарте).

**2026-09-05 вечер, вопрос юзера про архитектуру тиков (ответ: 4 варианта, для тестов поллинг ок):**
- Юзер спросил, хорош ли тик 1мс и какие альтернативы есть. Ответ:
  1. **Поллинг-поток 1мс** (текущий) — просто, работает; минус race с игровым потоком (микродёргание флагов между тиками), но для state-based эффектов (sprint-флаг) терпимо: 49 из 50 тиков флаг стоит.
  2. **Подписка на event bus мода** (самый элегантный, рекомендация для постоянных фич) — у форка Kotlin event bus (PlayerSneakEvent/PlayerSprintEvent реверсились); через reflection найти шину и зарегистрировать своего слушателя (класс доставляется нашим DefineClass) → код вызывается ВНУТРИ игрового тика в правильный момент, race исчезает, поллинг не нужен. Разовая работа по реверсу API шины (register + аннотация), потом переиспользуется для всех фич.
  3. **Байткод-инъекция в классы игры** — классический путь, НО у нас закрыт: JVMTI RedefineClasses/ClassFileLoadHook отключён форком (-3), классы игры грузятся из зашифрованного jar их лоадером. DR0+VEH на native работает, но Java-методы исполняются интерпретатором/JIT — hardware breakpoints на них ненадёжны.
  4. **ScheduledThreadPoolExecutor внутри JVM** — тот же поллинг, смысл менять нет.
- Решение: для AutoSprint-теста поллинг 1мс оставить; если тест пройдёт и пойдём делать набор постоянных фич — реверсить event bus мода и переходить на подписку (это и закроет race noslow).
